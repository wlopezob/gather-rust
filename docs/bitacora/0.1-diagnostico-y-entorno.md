### Diagnóstico inicial

- **Sólido:** move de ownership, `Result` y `?`, traits como interfaces, experiencia con Axum + sqlx + repository con traits.
- **A reforzar:** borrowing y `Copy` frente a move, lifetimes (lección 1.2), despacho estático frente a dinámico (1.4), modelo async de Tokio (2.2).
- Correcciones del diagnóstico:
  - `?` devuelve el error al llamador; `unwrap()` hace panic si hay error. En código de producción, `?` o `expect("motivo")`, nunca `unwrap()` sin pensar.
  - Un trait se parece a una interfaz de Java, pero se usa de dos formas: **estática** (`impl Trait` o genéricos: el compilador genera una copia por tipo, sin costo en ejecución) y **dinámica** (`&dyn Trait` o `Box<dyn Trait>`: llamada por vtable, como una interfaz en Java).
  - `async` no crea un hilo por tarea. Tokio corre muchas tareas sobre pocos hilos y cada tarea cede el control en cada `.await`, como el event loop de Netty o WebFlux. `std::thread::sleep` bloquea el hilo para todas las tareas: usa `tokio::time::sleep`, o `spawn_blocking` para trabajo bloqueante.

### Conceptos clave

- **Borrowing:** muchas referencias `&T` **o** una sola `&mut T`, nunca las dos a la vez (error E0502). El préstamo termina en el último uso de la referencia, no al cerrar el bloque. Con `&mut` nadie más puede ni siquiera leer.
- **Lifetimes:** un lifetime no cambia cuánto vive un valor; eso lo decide su dueño (al salir de scope se libera). El lifetime es la prueba que exige el compilador de que ninguna referencia se usa después de liberado el valor (E0597). En una firma como `fn mas_largo<'a>(a: &'a str, b: &'a str) -> &'a str` es un contrato: el llamador debe cumplirlo y el cuerpo de la función también. Si el compilador no puede deducir la relación entre entradas y salida, pide anotarla (E0106).
- **`'static` y `tokio::spawn`:** la tarea puede vivir más que la función que la lanza, por eso no puede capturar referencias a datos locales. Se le pasa la propiedad (`move`) o un `Arc`.
- **Workspace de Cargo:** no hay comando que cree un workspace virtual; el `Cargo.toml` raíz se escribe a mano. El orden importa: primero el `Cargo.toml` raíz, luego `mkdir crates`, luego `cargo new --lib crates/world-core`. Así el crate hereda `version.workspace = true` y compañía, y no se crea un `.git` anidado.

### Preguntas de defensa

**1. ¿Por qué hay un solo `Cargo.lock`, en la raíz? ¿Por qué va a git? ¿Cómo se logra lo mismo en Maven?**

- Tu respuesta: fija las versiones exactas con que se compiló; lo usan el pipeline y los otros devs, por eso va a git.
- Respuesta completa: Cargo lo crea o actualiza al resolver dependencias (`cargo build`, `cargo add`, `cargo update`) y guarda versión y checksum de todas, incluidas las transitivas. Hay uno solo porque el workspace resuelve una sola vez para todos los crates: todos usan la misma versión de cada dependencia y sus tipos son compatibles entre crates. La clave frente a Maven: en Cargo `serde = "1.0.200"` es un **rango** (`>=1.0.200, <2.0.0`), no una versión exacta. Sin lockfile, cada día podría bajar una versión distinta. Maven no tiene lockfile; la reproducibilidad sale de versiones fijas, `dependencyManagement`/BOM y `maven-enforcer` (Gradle sí tiene `dependencyLocking`). En CI se usa `cargo build --locked`, que falla si el lock no corresponde al `Cargo.toml`.

**2. Agregas `crates/protocol`: ¿qué cambias en el `Cargo.toml` raíz y cómo depende de `world-core`?**

- Tu respuesta: nada en la raíz, porque `members = ["crates/*"]` ya lo incluye; considerar `workspace = true`.
- Respuesta completa: para **registrar** el crate no se toca la raíz. Para la dependencia, `workspace = true` solo no compila (`workspace.dependencies was not defined`). Dos formas válidas:
  - Directa: en `crates/protocol/Cargo.toml`, `world-core = { path = "../world-core" }`.
  - Centralizada (la que usaremos, equivale a `dependencyManagement` del POM padre): en la raíz `[workspace.dependencies] world-core = { path = "crates/world-core" }` y en el crate `world-core.workspace = true`. Con esto `cargo add -p protocol world-core` escribe la línea por ti.
  - En `Cargo.toml` el nombre lleva guion (`world-core`); en el código, guion bajo (`use world_core::...`).

**3. ¿Qué controlan `edition = "2024"` y `rust-version = "1.99"`?**

- Tu respuesta: `rust-version` indica con qué versión de Rust se creó el proyecto; `edition` define reglas de sintaxis y advertencias, y mantiene la compatibilidad con código anterior.
- Respuesta completa: hay tres cosas distintas.

| Qué | Controla | Equivalente Java |
|---|---|---|
| `rust-toolchain.toml` | El compilador **exacto** que se usa (1.99.0) | `.sdkmanrc` o Maven toolchains |
| `rust-version` | La versión **mínima** soportada (MSRV). Con un compilador más viejo Cargo se niega: `rustc 1.99.0 is not supported by the following package: ... requires rustc 1.200`. Con `resolver = "3"` además prefiere versiones de dependencias compatibles con ese mínimo. | `requireJavaVersion` de `maven-enforcer` |
| `edition` | Las reglas del lenguaje que adopta **cada crate** (palabras reservadas, lints, prelude). El mismo compilador compila todas las ediciones y un crate 2021 puede ser dependencia de uno 2024. Se migra con `cargo fix --edition`. | Parecido a `maven.compiler.release`, pero solo cambia reglas del lenguaje, no la API de la librería estándar |

  `rust-version` no es "con qué versión se creó": eso lo fija `rust-toolchain.toml`. Cuando subas el toolchain, sube también `rust-version`.

**4. ¿Qué cambia entre los perfiles `dev` y `release`?**

- Tu respuesta: release es el compilado final para producción.
- Respuesta completa (valores por defecto según el Cargo Book):

| Ajuste | `dev` (`cargo build`) | `release` (`cargo build --release`) |
|---|---|---|
| `opt-level` | 0, sin optimizar | 3, todas las optimizaciones |
| `debug` (símbolos) | sí | no |
| `debug-assertions` (`debug_assert!`) | activas | desactivadas |
| `overflow-checks` | activos | desactivados |
| `incremental` | sí | no |
| Carpeta | `target/debug` | `target/release` |
| Resultado | compila rápido, binario lento | compila lento, binario rápido |

  Bonus (probado): una suma `u8` que pasa de 255 en tiempo de ejecución hace panic en `dev` (`attempt to add with overflow`) y en `release` da `0` sin avisar. Regla senior: no depender del perfil y decir la intención: `checked_add` (devuelve `Option`, como `Math.addExact` pero sin excepción), `wrapping_add` (números de secuencia), `saturating_add` (topes). En Java un `int` siempre da la vuelta sin avisar.

**5. ¿Un lifetime puede hacer que un valor viva más tiempo?**

- Tu respuesta: no puede hacer que un valor viva más tiempo.
- Respuesta completa: correcto. El dueño decide cuánto vive el valor; el lifetime solo permite al compilador comprobar que ninguna referencia lo sobrevive. Si no puede probarlo, no compila. Corrige con tus palabras la frase de "Mis notas".
